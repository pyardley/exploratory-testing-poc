# Findings: Is Automating Exploratory Testing Feasible?

Source notes from building and iterating on an AI-augmented exploratory testing PoC. Written to preserve lessons learned before they evaporate — intended as raw material for a blog post, not the post itself. Organized by theme, not chronology. Direct data points are marked; interpretation is marked as interpretation.

Repo: `exploratory-testing-poc` (this project). All file paths below are relative to its root.

---

## 1. The experiment, in one paragraph

We built a deliberately buggy test web app ("WidgetWorks" — a small-business inventory catalog) with 40 hand-seeded defects spanning Michael Bolton's FEW HICCUPSS consistency heuristics plus a CRUD-specific checklist, none of them signposted (no filenames like `bad_field_alignment.html`, no comments, no giveaway labels). We then built a tool (`exploratory-tester/`) that explores *any* site — deterministic Playwright scanners first, headless `claude -p` AI review second — and produces session notes like a human exploratory tester would write, without ever being shown the answer key. A separate `comparison/` package, which is the *only* code allowed to read the answer key, scores a tester run against it via its own independent LLM adjudication pass. The question throughout: how much of this can be automated, how well does it actually work, and where does it fall down.

## 2. Architecture choices that mattered

- **Deterministic-first, AI-second, not AI-only.** Every scanner runs and captures a fixed evidence bundle (screenshots, DOM, console/network logs, an axe accessibility scan, extracted text) *before* any LLM call. The AI phase only ever reviews that frozen bundle — no live browsing, no MCP tools, `--tools Read` scoped to nothing but the evidence directory. This was a deliberate bet that most of the "boring but valuable" 80% of exploratory testing (broken links, console errors, accessibility violations, visual drift) doesn't need an LLM at all, and paying for one to look at everything is both expensive and less repeatable than a plain script.
- **Static artifact review, not agentic browsing.** We explicitly chose *not* to let the AI drive the browser itself, even though that's the more "authentic" simulation of a human tester. Reasoning: repeatability. A fixed evidence bundle produces comparable results run-to-run; an agent choosing its own path through a site does not, which matters a lot when you're trying to score effectiveness against a fixed answer key.
- **Headless CLI over API key.** The AI phase shells out to the already-authenticated `claude` CLI (`claude -p`) rather than calling the Anthropic API directly. No key management, reuses the existing login. This is a portability trade-off — it only works where the CLI is installed and authenticated — but for a PoC on one's own machine it removed an entire class of setup friction.
- **Answer-key isolation as defense in depth, not a single check.** The fault catalog lives in a sibling directory never referenced by the tester's source code; the tester's only filesystem grant is its own evidence directory; a runtime realpath check hard-aborts if any configured input path resolves under `answer-key/`; and a comparison-only-reads-it-after-the-fact rule is enforced structurally (different package, different process). No single point of failure was trusted to prevent cheating.

## 3. Baseline result (before any of the fixes below)

One full, clean run (`exploratory-tester/runs/measured-run-3/`) scored against all 40 seeded faults:

| Metric | Result |
|---|---|
| Found | 20 / 40 (50%) |
| Partially found | 7 / 40 (18%) |
| Missed | 13 / 40 (33%) |
| **Recall** (found + 0.5×partial) | **59%** |
| False positives | 8 (mostly defensible — design-choice disagreements) |
| Bonus findings (real, unseeded defects) | 9 |
| Caught by deterministic scan alone | 1 of 27 caught faults |
| Caught by AI review alone | 20 of 27 caught faults |
| Caught by both | 6 of 27 caught faults |

**Interpretation:** in the baseline architecture, the AI layer was doing almost all of the actual detection work. The deterministic layer was closer to an evidence-gathering pass than an independent detector — valuable for anchoring/confirming what the AI found (broken links, axe violations, colour drift), but not finding much on its own. This is an important data point against the naive assumption that "deterministic-first" automatically means "deterministic does the heavy lifting."

## 4. The single biggest structural finding

**Nearly every miss shared one shape: the fault only becomes visible if you actually *perform* the interaction and check the outcome.** Examples from the baseline run:

- A sort dropdown labeled "Price: Low to High" actually sorted high-to-low — invisible unless you select it and read the resulting order.
- A search box was wired to nothing — invisible unless you type something and check whether results change.
- A "Next" pagination button did nothing — invisible unless you click it and check whether the page advances.
- A notification checkbox saved inverted — invisible unless you toggle it, save, reload, and compare.
- A Save button had no double-submit guard — invisible unless you click it twice rapidly and watch for a race.

A screenshot and a DOM snapshot, however good, cannot show the *after* state of an action that was never taken. This is a ceiling on "static artifact review" as an architecture, not a bug in any one scanner — **and it turned out to be fixable**, which is the most encouraging finding in this whole project (see §6).

## 5. Engineering pitfalls found while building this (useful regardless of the exploratory-testing angle)

These cost real debugging time and are worth remembering for anyone building similar Playwright/Claude-CLI tooling:

1. **Git Bash silently mangles CLI arguments that look like absolute Unix paths.** `--golden-path /index.html` invoked from Git Bash got rewritten to a local Windows filesystem path *before Node ever saw it* (MSYS path conversion), sending a `page.goto()` at a dead file path with `waitUntil: 'networkidle'` — which then hangs forever, because a request that never resolves never goes idle. No error, no timeout, just a silent hang. Fix: `MSYS_NO_PATHCONV=1` env var, or avoid leading-slash args from Git Bash entirely.
2. **Windows has a hard command-line length limit that large LLM prompts reliably exceed.** Passing a big prompt as a `-p "<prompt>"` CLI argument works fine until the prompt gets large (e.g. a cross-page synthesis call embedding every per-page finding) — then it fails with "The command line is too long," a Windows `CreateProcess` limit, not a Node or Claude Code limit. Fix: pipe the prompt over stdin instead of passing it as an argument. Stdin has no such ceiling. This should be the default design for any tool piping non-trivial content into a CLI subprocess.
3. **Playwright's `page.screenshot()` has a default behavior that can poison a concurrently-captured DOM snapshot.** By default, screenshots hide text-input carets by injecting `caret-color: transparent !important` into every input for the duration of the capture, then removing it. Running `page.screenshot()` and `page.content()` concurrently (`Promise.all`) caught the DOM mid-mutation — the "temporary" style got captured as if it were real production markup. The AI review dutifully (and wrongly) reported it as a serious, systemic, cross-page accessibility bug, appearing in 6+ separate findings across different pages. Fix: `caret: 'initial'` on the screenshot call, and more generally — **don't run anything that mutates the DOM, even transiently, concurrently with anything that reads the DOM for evidence.** This is a general lesson: any library convenience feature that touches the DOM "just for a moment" is a landmine for concurrent evidence capture.
4. **Client-side caching in the target app can silently defeat a diff-based bug scanner testing that same app.** A before/after diff scanner (built to catch "editing record A actually changed record B") kept coming back empty even though the underlying bug was confirmed present by hand. Root cause: the page being diffed cached its list client-side in `sessionStorage` (itself a separate, real, deliberately-seeded bug) and reused the cache across every navigation *within the same browser session* — so "before" and "after" snapshots were reading the same frozen cache regardless of what actually changed server-side. Fix: the diffing scanner now explicitly clears `sessionStorage`/`localStorage` and forces a reload before every snapshot it takes for comparison purposes. **Two independent bugs can mask each other in a way that's non-obvious until you trace through exactly what each snapshot call actually saw.**
5. **A test probe's own synthetic data can defeat the probe, if the target app sorts data.** A bug-hunting scanner tagged its synthetic test records with a `"ZZZ-PROBE-..."` prefix for easy identification. On a catalog sorted alphabetically ascending, renaming a record to start with "Z" sorts it to the *very end* of the list — often off a paginated first page entirely. So even when the underlying "wrong record got updated" bug fired correctly, the affected record vanished from the visible page instead of visibly changing, and the diff saw nothing. Fix: use an `"AAA-"` prefix instead, so a renamed record sorts to the *front* and stays visible. This is a real trick working QA engineers use, discovered here the hard way. **When your test tooling generates its own probe data, the data's own properties (like sort order) can interact with the system under test in ways that hide the very bug you're trying to surface.**
6. **Automated accessibility scanners have real, documented blind spots — and it's not a configuration problem.** A form whose inputs relied entirely on `placeholder` text (no `<label>`) was expected to trip axe-core's "label" rule. It didn't, on any configuration. Root cause: WCAG's accessible-name computation credits `placeholder` as a fallback name when nothing else is present, so axe correctly reports "this element has *a* name" even though that name disappears the moment the user starts typing — a well-known real-world gap between "passes automated a11y scanning" and "is actually accessible." This is precisely the kind of thing that needs human (or AI) judgement layered on top of automated tooling, not a scanner bug to fix.
7. **Nested project subagents aren't discovered by a session rooted one level up.** Running `npx playwright init-agents --loop=claude` inside a subdirectory (`regression/`) of a larger repo produces real `.claude/agents/*.md` definitions — but a Claude Code session working from the *parent* directory can't see or invoke them (`Agent type 'X' not found`). Claude Code's project-agent discovery scans the project root's own `.claude/`, not arbitrary subdirectories'. To get the live agent loop, you have to actually run `claude` with that subdirectory as your working directory/project root — a separate session, not a nested call from the outer one. This matters for anyone trying to compose multiple "Playwright agent" scaffolds inside one larger monorepo.

## 6. What happened after fixing the structural gap (§4)

Built a new scanner (`interactionProbe.js`) that actually *performs* the interactions instead of just describing static state: selects every option on dropdowns and diffs the result (with a generic "does the claimed sort direction match the observed order" check via regex-extracted price tokens — no knowledge of the specific page needed), types into search-like inputs and checks whether anything changes, clicks "Next"-style pagination and checks a "Page X of Y" status/content actually changes, and round-trips checkboxes through a save + fresh reload to catch both "didn't persist" and "persisted inverted."

**Directly verified (via inspecting scanner JSON output, independent of any LLM call) — these previously-missed-or-AI-only-caught faults are now caught by pure deterministic scanning, zero AI cost:**

- Sort direction claim vs. actual order mismatch (previously missed entirely)
- Dead search box — no content change on a query (previously missed entirely)
- Dead pagination — no change on "Next" despite "Page 1 of 3" (previously only found via AI narrative)
- Inverted checkbox persistence (previously missed entirely)
- Identical generic error text across two different validation failure scenarios (previously missed entirely) — via extending `formValidation.js` to run a second scenario (a non-numeric value in a numeric-looking field) alongside the original empty-submit scenario, and comparing actual captured error text, not just a boolean
- Index-vs-id "wrong record updated" bug — via broadening the CRUD smoke flow to test update against 3 distinct records and diff the *entire* visible list (not just the intended record), catching a record that becomes newly visible after being renamed even if it wasn't visible before
- Missing double-submit guard on Save (rapid double-click) — via an explicit race-condition probe added to the CRUD smoke flow

**Interpretation:** this is the most important result in the whole project. The "structural ceiling" in §4 was not actually structural — it was a scope gap. Once the scanners were extended to *act* rather than only *observe*, roughly half of the previously-missed faults became deterministically catchable, at zero marginal LLM cost per run. This significantly shifts the cost/reliability profile: a larger fraction of defect-finding can now happen via cheap, fast, perfectly-repeatable scripted checks, with the (still real, still valuable) AI layer reserved for genuinely judgement-dependent heuristics — Claims, brand feel, whether copy oversells a feature, cross-page contradictions in tone.

**Confirmed with a full re-run + independent re-adjudication** (`exploratory-tester/runs/measured-run-4/`, scored in `comparison/reports/2026-09-04T17-06-47-139Z-comparison-report.md`, against the 41-fault catalog including `H-04` from §7):

| Metric | Baseline | After fixes | Delta |
|---|---|---|---|
| Recall (found + 0.5×partial) | 59% | **71%** | +12 points |
| Found outright | 20/40 (50%) | 28/41 (68%) | +18 points |
| False positives | 8 | 4 | halved |
| Bonus findings | 9 | 11 | +2 |
| Caught by deterministic scan alone | 1 of 27 caught | 4 of 30 caught | ~3x |
| Caught by both layers | 6 of 27 caught | 14 of 30 caught | >2x |
| Caught by AI alone | 20 of 27 caught | 12 of 30 caught | fewer, but overall recall still rose |

Category-level, every category that scored 0% found in the baseline reached 100% found after the fixes: User Expectations (1/3 → 3/3), CRUD-Update (0/2 → 2/2), CRUD-Read/pagination (0/1 → 1/1), Explainability (0/3 → 2/3). The overall recall rising *while* the AI's alone-share of catches fell is the key number here — it means the deterministic additions weren't just duplicating what AI review already found, they found things the AI review had genuinely missed.

## 7. A deliberate experiment: can this catch a regression against its own history?

After the initial 40-fault baseline was committed to git, we deliberately introduced a 41st fault as a *second commit*: silently changing the golden reference page's own primary brand color via an inline CSS override, with a plausible, non-giveaway commit message ("Adjust homepage primary color token"). This was designed to be uncatchable by the existing architecture on purpose, to probe a specific edge:

**Why it's uncatchable by design:** every visual-consistency check in the tool works by comparing *other* pages against whatever the golden reference page currently shows. If the golden page itself regresses, there is no same-snapshot comparison that can notice — worse, a well-designed consistency scanner would likely start flagging every *other* (still-correct) page as "deviating from golden," which is backwards from reality. The only way to catch this fault is diffing against git history (`git log -p`, or comparing to a tagged prior release) — a capability the tool does not have.

**Interpretation:** this crystallizes a real limitation of "consistency-based" exploratory testing generally, automated or human: heuristics like Familiarity, Image, and Comparable Products are only as good as the reference they're compared against. If the reference itself silently drifts, the whole apparatus can point in the wrong direction. Michael Bolton's "History" heuristic — is the software consistent with its own past? — is not reducible to any of the other consistency heuristics; it requires an oracle outside the current snapshot entirely (version control, a changelog, a prior release). This is a concrete, unimplemented capability gap worth naming explicitly in any writeup: **none of the current scanners are git-history-aware**, and that's a distinct kind of testing from everything else in this PoC.

**Confirmed, not just predicted.** When this fault was actually scored (`H-04` in `comparison/reports/2026-09-04T17-06-47-139Z-comparison-report.md`), the independent adjudicator's own reasoning read: *"This fault requires git-history diffing which the tool does not do. The tester's golden reference used the (regressed) current Home page, so index.html was treated as correct and all other pages were reported as drifting instead — exactly the perverse inversion the seeded fault documents."* This is a rare case of a predicted failure mode being independently verified, in the adjudicator's own words, exactly as designed. Good material for the post: it's a specific, falsifiable claim that was actually falsified-or-confirmed, not a hand-wavy limitation.

## 8. The road not taken, taken anyway: a live agentic MCP-browsing experiment

Recall §2's architecture bet: "static artifact review, not agentic browsing" — the AI phase reviews a frozen evidence bundle rather than driving a live browser itself, explicitly for repeatability. We went back and actually ran the road not taken, to get real data instead of a hunch: how many of the still-missed faults can a live, MCP-driven agent catch by actually clicking around like a human, and at what cost?

### Setup

Built a separate, clearly-labeled experimental module (`exploratory-tester/src/agentic/`, kept fully apart from the default pipeline) that spawns headless `claude -p` calls wired to the real `@playwright/mcp` server instead of a fixed evidence bundle — the model gets live browser tools (`browser_navigate`, `browser_click`, `browser_type`, `browser_select_option`, `browser_snapshot`, `browser_evaluate`, `browser_handle_dialog`, etc.) and nothing else (no Read/Bash/Write — `--tools ""`, `--strict-mcp-config`, `--permission-mode bypassPermissions` since there's no TTY to approve prompts interactively). Rather than one open-ended "explore the whole site" session, we ran **6 separate, bounded tasks**, each covering an area phrased around checklist activities, never fault IDs (e.g. "try the sort control, search box, and pagination on the Catalog page" — not "test whether sort is broken"). Bounding it this way was itself a lesson learned from spiking the approach first (see below).

### Getting it working was not trivial — real negative findings before a single "real" run happened

- **The first spike attempt silently failed.** A `claude -p` call configured with the MCP server responded "I don't have a browser tool available" after a single fast turn — the MCP server (which has to cold-start a real headless browser as a subprocess) hadn't finished initializing before the model gave up. No error was surfaced; it just proceeded as if the tool didn't exist.
- **The model can hallucinate tool calls as plain text instead of failing loudly.** On a harder multi-step task, one spike attempt produced literal `<function_calls><invoke name="Bash">...` XML-like text embedded in the final answer — the model attempting to call a tool that was explicitly disabled (`--tools ""`), getting no real execution, and then confidently reporting a fabricated conclusion ("the server does not appear to be running") that was flatly false — the server was actually up and had just been successfully used moments earlier in the same testing session. This is a materially different failure mode from a clean error: it's a wrong, confident answer with no signal that anything went wrong.
- **The fix was explicit prompt engineering, not a config flag.** The task prompt template ended up with hard-coded operating notes: state plainly that only MCP browser tools exist, that Bash/Read/Write do not exist and must not be attempted, and instruct at least one retry before concluding the target is unreachable. This closed the gap in practice — every one of the 6 real task runs later showed the exact same "first `browser_navigate` call fails, identical retry succeeds" pattern in its self-reported tool-reliability notes, and none of the 6 hallucinated a tool call again. **This cold-start-then-retry pattern was 6-for-6 consistent** — reproducible enough to treat as a known, characterized quirk of this specific architecture (a fresh MCP server subprocess per session) rather than a one-off flake.
- **Smaller tool-surface gaps surfaced too:** `browser_triple_click` doesn't exist (worked around with click + select-all + retype), and ref-based element selectors occasionally failed with "Unknown engine" errors (worked around by falling back to CSS selectors). Neither was fatal, but both cost retries/turns.

### Positive findings: real, otherwise-invisible catches

Scored the resulting session (`exploratory-tester/runs/agentic-run-1/`) against the same 41-fault answer key via `comparison/reports/2026-09-05T11-23-07-071Z-comparison-report.md`. Of the 11 faults still missed after every fix in §6, this single run caught:

- `E-03` (edit save gives no feedback), `H-03` (timestamp never advances), `P-03` (dead PDF download), `S-04` (sort control not keyboard-operable), `CRUD-01` (negative price accepted) — all outright **FOUND**
- `CL-01` (contradictory customer-count claims) — **FOUND**, matching the static AI's baseline catch
- `H-04` (the golden-page History regression from §7) — **PARTIALLY_FOUND**, and how it got there is the single most interesting result of this whole experiment (see below)

That's 6 outright + 1 partial out of the 11 hardest remaining faults, in one run, at zero engineering effort beyond the prompt (no new scanner code) — a real demonstration that some categories of defect are more accessible to "have an agent actually behave like a curious human" than to any amount of scripted scanning.

### The `H-04` result deserves its own paragraph

§7 predicted this fault was uncatchable by *any* approach that lacks git-history awareness, reasoning that a live session has "nothing to compare the golden page against." That reasoning was subtly wrong, and the agentic run is what exposed the error: the golden-color override only touched `index.html` — every *other* page still legitimately used the true original color. That's a same-session, cross-page inconsistency, fully visible without touching git at all. The agent's `browser_evaluate` calls across Home, About, and Catalog *did* notice `--color-primary` differs between pages. But it then concluded, in its own words, that "the Home page is the canonical brand reference" per the charter, and that the *other* pages were the ones drifting — the exact opposite of the truth, since Home is the page that actually regressed. The adjudicator's verdict reasoning states this precisely: *"Tester detected the color mismatch symptom but attributed it to About/Catalog pages being wrong, believing Home is canonical. In truth Home is the regressed page. Symptom found, cause direction wrong."*

The sharper, corrected lesson for the post: it's not "git-history-blind tools can never catch a golden-page regression." It's **"a tool (or tester) that treats one page as ground-truth-by-definition, rather than checking which page agrees with the majority, will confidently misdiagnose a regression on that one page — and a live agent doing the same is subject to the identical bias if it trusts the same designated authority."** The failure is about which oracle you trust, not about whether you're a script or an LLM.

### Negative findings: cost, time, and a lower — not higher — overall score

| | Static + deterministic (§6, `measured-run-4`) | Agentic MCP browsing (`agentic-run-1`) |
|---|---|---|
| Recall (41-fault catalog) | **71%** | 57% |
| Cost | ≈$0.50–0.70 (9 pages + synthesis, Sonnet) | **$3.04** (6 tasks, Sonnet) — roughly **5–6x** |
| Wall-clock time | a few minutes | **1402s (≈23.4 minutes)** — roughly **6–8x** |
| False positives | 4 | 2 |
| Bonus findings | 11 | 6 |

Despite catching several things the other approach misses, the agentic run's *overall* recall was lower, not higher, than the current hybrid pipeline — and lower even than the original pre-fix baseline (59%). The reason is coverage shape, not quality: 6 broad, judgement-driven tasks in ~23 minutes cannot exhaustively check every element the way a scripted scanner checks every button's computed CSS or every form's field-by-field validation. The agentic run missed several faults the deterministic/static pipeline catches reliably every time: `U-01`/`U-02` (interaction round-trips), `C-01`/`C-02`/`C-03` (precise CSS/font drift), `F-02` (button class), `I-04` (missing favicon), `E-01` (identical-error-text-across-scenarios, which requires deliberately trying two distinct failure modes and comparing exact text — this run tried a negative price but never tried an empty required field). None of these are things a careful human would necessarily miss either — they're the kind of check that benefits from a script's willingness to be exhaustive and precise about the boring stuff, which an attention/judgement-driven session, human or AI, naturally deprioritizes in favor of broader coverage.

**Complementarity is the real headline, not either number alone.** Between the two approaches, only 4 of the 41 faults were missed by *both* (`F-03`, `I-01`, `I-02`, `CRUD-03`) — meaning a combined run would land around 90% recall, well above either approach individually. The two methods have different, only partially-overlapping blind spots: deterministic/static review is precise and exhaustive about static structure and simple round-trips; live agentic browsing is better at things that only become visible by comparing multiple live pages against each other symmetrically, or by improvising a slightly unusual interaction sequence a scripted scanner wasn't specifically written to try.

### A verdict on this specific question, for the post

Live agentic MCP browsing is not a drop-in upgrade to the default pipeline — at 5–6x the cost and 6–8x the time for *lower* aggregate recall, it would be a bad default. But it is a genuinely valuable **supplementary** pass: cheap enough to run occasionally (a few dollars, not a production line item) for the specific things it's disproportionately good at — multi-page consistency checks that don't privilege one page as ground truth, and behavioral checks that reward general curiosity over scripted precision. The honest framing is "periodic deep-dive audit," not "replacement for the fast, cheap, exhaustive pass."

## 9. External validation on a genuinely independent site (Sauce Demo)

§8's open-questions list flagged the obvious gap: everything so far was validated against WidgetWorks, an app built by the same process as the tool itself. So we pointed the unmodified tool at a real, independent, publicly-known-buggy site — **Sauce Demo** (`saucedemo.com`, "Swag Labs"), a well-known e-commerce practice app whose `problem_user` login is deliberately seeded with real defects, built by an entirely different team for an entirely different purpose. This is the single most important validation exercise in the whole project, and it did not go smoothly at first — which is exactly why it's worth documenting in full.

### Three real generalization gaps, found and fixed in sequence

Pointing the tool at Sauce Demo immediately broke it, three times, in three different ways — each one a genuine, previously-invisible assumption baked into the tool, because WidgetWorks never exercised it:

1. **Login.** WidgetWorks has no authentication at all, so the tool never needed to handle it. Sauce Demo requires logging in before there's anything to explore. First attempted fix: a Playwright `storageState` (pre-captured cookies) passed via a new `--storage-state` flag — this is the standard Playwright pattern for skipping a login flow, and it seemed like the obvious answer. It didn't work: Sauce Demo's client-side app doesn't consult the session cookie on page load to auto-redirect an already-authenticated visitor away from the login view — it only routes away in direct response to a real form submission. A valid cookie sitting in the browser is simply never checked. **Fix:** a `--login-url`/`--login-username`/`--login-password` bootstrap that performs a real login (generic selectors: a `password`-type input as the reliable anchor, the first text/email input sharing its form for the username) before crawling begins, in the same browser context the whole scan then reuses.
2. **Client-side routing.** Even freshly authenticated, a direct navigation to `/inventory.html` returned a genuine, unconditional 404 — not an auth gate, an actually-missing server route. Sauce Demo is a client-routed SPA: the URL only changes via `history.pushState` after in-app navigation, and the server has no rewrite rule serving that path directly. The tool's entire crawler was built around "every discovered URL is independently re-navigable," which is simply false for this architecture. **Fix:** `crawler.js` now falls back to click-path reconstruction whenever direct navigation to a same-origin URL fails — it remembers the sequence of element clicks that reached a page from its nearest directly-reachable ancestor, and replays that sequence (navigate to the ancestor, click each step in order) instead of re-navigating by URL. `scan.js`'s per-page evidence loop and the golden-reference pass both use the same mechanism, so this is a single, consistent capability, not a special case bolted onto one code path.
3. **`href="#"` navigation.** Even with click-path replay working, the crawler still found nothing to click — because every internal navigational element (product links, the cart icon, the sidebar menu) uses `href="#"` with the real routing logic living in a JavaScript `onClick` handler, a standard React pattern. The crawler's link discovery explicitly filtered out `href="#"` (originally to avoid false "dead anchor" positives on ordinary sites). **Fix:** the crawler now also discovers `href="#"`/no-href elements that carry a stable `id` or `data-test`/`data-testid` attribute, and — since there's no static attribute that reveals where they lead — actually clicks each one to observe whether the URL changes, treating a same-origin URL change as a newly-discovered page. Click-path steps are now full CSS selectors (`#id`, `[data-test="..."]`, or `a[href="..."]`) computed once at discovery time, not raw hrefs, so real links and click-only navigation replay through the exact same mechanism.

All three fixes are general — nothing Sauce-Demo-specific is hardcoded — and none of them change behavior for a traditional multi-page site like WidgetWorks at all: `clickPath` stays empty and every page resolves via plain direct navigation exactly as before, since WidgetWorks's links all work as real hrefs. The fallback paths only ever activate when the fast path genuinely fails.

### The result, once it worked

With those three fixes, the crawler discovered 8 pages (7 of them exclusively via click-path reconstruction — direct navigation only ever worked for the login-landing page itself) and deduplicated them to 3 distinct templates (inventory/catalog, cart, item detail). A full run (deterministic scanners + `claude -p` review, `exploratory-tester/runs/saucedemo-full-1/`) against `problem_user` found, with zero prior knowledge of this app's bugs and zero hand-tuning for it:

- **The interaction-outcome prober (§6) caught a real bug entirely deterministically, before any AI call ran at all:** the catalog's sort `<select>` — all four options (Name A-Z/Z-A, Price low-high/high-low) produce byte-identical output. `allSelectionsProducedIdenticalContent: true`, plus a `directionClaimMismatch` on the "low to high" option. Zero LLM cost for this catch.
- **The AI review independently found what is, by community reputation, *the* single most famous `problem_user` bug in Sauce Demo**: all six different products — a backpack, a bike light, a t-shirt, a jacket, a onesie — render the exact same placeholder photo of a pug dog holding a tennis ball. It found this from a screenshot with no hint about what to look for beyond the checklist's Image/World heuristics, and articulated exactly why it matters: "a bike light and a backpack cannot look identical."
- Several other findings that check out against the live site: the sidebar's "About" link pointing to a real dead `saucelabs.com/error/404` URL (confirmed present in every page's DOM, correctly flagged as a cross-page/global-component defect rather than three separate findings), a fully-enabled Checkout button on an empty cart, a completely unlabeled `<select>` (a real, critical axe violation), and a systemic absence of semantic heading elements site-wide.
- The session notes correctly distinguished **global/template-level defects that repeat across every page** (About link, missing headings, unlabeled cart icon, generic `<title>Swag Labs</title>` everywhere) from page-specific ones, and — consistent with the calibration noted in §3 — flagged some observations as genuinely uncertain rather than asserting them (e.g. explicitly noting the evidence bundle didn't include enough to confirm whether the item-detail page's product image was also broken, only that the catalog's definitely was).

### Why this matters more than any single number in this document

Every other result in this document — recall percentages, false-positive counts, cost figures — was measured against an answer key describing bugs the tool's own author (i.e., this session) deliberately planted. That's necessary for rigorous measurement, but it can't fully rule out the tool being unconsciously well-matched to its own test app. This run has no answer key and needed none: the tool surfaced a bug independently corroborated by the QA community's general knowledge of this app, using the exact same unmodified checklist, charter, and scanners built for a small-business inventory site with a totally different page structure, no authentication, and no client-side routing. That's the strongest evidence in this whole project that the approach generalizes rather than having been quietly overfit to WidgetWorks.

The honest caveat: getting here took three rounds of the tool breaking and being fixed. "Point this at any site" was not true out of the box — it's true now, for sites that fit the patterns this update added (form-based login, client-side routing via pushState, `href="#"` + click-handler navigation). A site with a fundamentally different auth mechanism (OAuth redirects, MFA) or a different SPA routing convention (hash-based routing, a framework router with no discoverable click targets at all) would likely surface a fourth gap. That's not a weakness to hide — it's the actual shape of what "generalizes to any site" costs in practice: not zero engineering, but engineering that pays off across every future site sharing the same pattern, discovered by testing against something real rather than assumed in advance.

## 10. A second external validation, with an entirely different architecture (Shady Meadows B&B / restful-booker-platform)

One independent site is real evidence but not exhaustive evidence for "generalizes to any site" (see §12's open question on this below). So a second, structurally distinct external target was set up: **Shady Meadows B&B**, the demo front end of Mark Winteringham's `restful-booker-platform` — a real, actively-maintained, seven-microservice hotel-booking training app (auth/booking/room/report/branding/message services plus a Next.js front end), self-hosted locally via `docker compose up --build` rather than reachable as a public hosted site like Sauce Demo. Getting it running required its own engineering detour, then the tool ran against it exactly as designed, with no site-specific code changes.

### Getting it running: a Windows/Docker detour, not a testing-methodology one

A first attempt at this app (earlier in this project) hit a wall on host-installed Maven/JDK version mismatches and was abandoned in favor of Sauce Demo. The retry solved it differently: instead of installing Maven/JDK 26 on the host, the six Java services were built inside a disposable `maven:3.9-eclipse-temurin-26` container (`docker run -v "$(pwd):/workspace" ... mvn -B package -DskipTests`), writing JARs straight onto the host filesystem for `docker compose build` to pick up — no host toolchain changes needed. Two Windows/Git-Bash-specific snags recurred here that had already been seen and fixed once before in this project (for `claude -p` invocations): MSYS silently rewriting a leading-slash Docker argument (`-w /workspace`) into a bogus local path, fixed with the same `MSYS_NO_PATHCONV=1` prefix documented in the README; and the 7th module (`assets`, the Next.js front end) failing to build inside the Maven-only container because it needs `npm`, not `mvn` — resolved by simply not caring, since `assets/Dockerfile` turned out to be a fully self-contained multi-stage Node build with no dependency on the Maven step at all. `docker compose up -d --build` then brought up all 7 containers cleanly.

### What the run looked like — and what it didn't need

`exploratory-tester` was pointed at `http://localhost` (the `rbp-assets` Next.js service, mapped to host port 80) with the unmodified WidgetWorks checklist/charter/app-description — the same invocation shape as every other run in this document, `node bin/cli.js --url http://localhost --golden-path / ...`, no flags specific to this site. Unlike Sauce Demo, **none of the three generalization fixes from §9 were needed**: every route — the hash-anchored nav items (`/#rooms`, `/#booking`), the dynamic reservation pages (`/reservation/1?checkin=...`), the legal pages (`/cookie`, `/privacy`) — resolved via ordinary direct navigation. The crawler's SPA click-path fallback never activated (zero pages reached via click-path reconstruction); this is a hybrid SSR/CSR Next.js app, not a client-only-routed SPA, and it shares no tech stack with either WidgetWorks or Sauce Demo. That's a useful data point on its own: the ordinary fast path continues to work cleanly on a third, independently-built app. The admin login page (`/admin`) was visited and evidence-captured as an ordinary anonymous page — this run deliberately did not attempt the `admin`/`password` login, so whatever exists behind it (the AI review's own open questions ask exactly this) is unexplored territory for a future session.

### What it found

- **The headline finding, and the most severe of any external-validation run so far: the site's entire booking conversion path is broken end-to-end.** All three "Book now" CTAs on the home page link to `/reservation/1`, `/reservation/2`, `/reservation/3`; every one of them renders nothing but a permanent Bootstrap spinner with no error message, no retry, no fallback. The AI review caught this from the evidence bundle alone (screenshot = spinner, extracted text = empty, one console error, one bad network response) and ranked it the #1 cross-page finding without being told to look for it.
- **Independently confirmed as a genuine, reproducible full-stack defect — not a Docker artifact of this local bring-up.** The captured network log pinpoints the exact failing request: a same-origin `GET /api/room/1` returning `500` with a *non-JSON* body (`"Internal Server Error"`), which is what breaks the client's `response.json()` call and leaves the spinner stuck forever. Checked directly against the running stack as a sanity check (not part of the tool's own process): `rbp-room` (the upstream microservice, up 3+ hours by the time of the check — ruling out a cold-start race) returns a perfectly valid `200` with real room data for the same ID, on the same host, at the same moment `/api/room/1` still 500s. Reading `assets/src/app/api/room/[id]/route.ts` in the app's own source shows a normal try/catch proxy handler that should return valid JSON on every path — meaning the observed bare-text 500 is an *uncaught* failure Next.js's own default error handler is rendering, not this route's own well-formed error branch. The room-*list* endpoint the home page uses works fine; only the single-room detail proxy is broken. This is exactly the kind of precise, evidence-backed defect report a human exploratory tester would want — found here with zero prior knowledge of this app's internals.
- **A second, different-flavored version of the "two pages disagree" pattern first seen on Sauce Demo (§9) — this time on legal/compliance content, not marketing copy.** The Cookie Policy names "Automation in Testing Online" as the data controller; the Privacy Policy names a different entity, "MW Test Consultancy" at a different domain. Neither is correct (Shady Meadows B&B should be the controller), and critically, they don't even agree with *each other* — two legal documents on the same site contradicting each other about who's responsible for user data. Caught by the cross-page synthesis pass, invisible from either page alone.
- **Deterministic scanners caught real, specific accessibility and content defects with no AI judgement needed**: all three room-card images carry `alt="Single Room"` regardless of actual room type (axe + DOM evidence); the contact form's `<label for="message">` doesn't match its textarea's `id="description"`; the booking date pickers have visible labels with no matching `id` on the actual input; footer link and Logout-button color contrast both fail WCAG AA; three social-media icons have no accessible name at all and all dead-link to `#`.
- **The `/admin` page renders as a visibly different product** — a dark, unstyled Bootstrap shell branded "Restful Booker Platform Demo" with completely different nav, versus every other page's "Shady Meadows B&B" white navbar. Flagged under Familiarity/Image/Comparable Products as a likely deployment-template mismatch; genuinely a known rough edge of this app's admin panel, not a scanner artifact.
- **A new, honest self-correction, distinct from anything seen on WidgetWorks or Sauce Demo: the AI review noticed the run's own inputs didn't match the target.** This run reused the WidgetWorks checklist/charter/app-description unmodified (deliberately — that's what "point the tool at any site" is supposed to mean), and more than once the AI review flagged the mismatch itself rather than silently forcing WidgetWorks-shaped judgement onto a hotel-booking site: *"the page title references 'Restful-booker-platform demo' while the charter describes 'WidgetWorks' — is this page from a different application than the one chartered, and if so, should it be in scope for this session?"* This is the same calibration property noted in earlier findings (README Conclusion #6) showing up in a new, sharper form — the tool questioning its own oracle rather than blindly trusting it.
- **A genuine false positive worth naming precisely, because it's informative rather than embarrassing.** The CRUD smoke flow's "Create" step found no page matching WidgetWorks' list+create-form shape, fell back to the home page itself, filled and submitted whatever generic form it found there (almost certainly the booking or contact form — neither of which has any "list" concept), then reported that the probe's tag value "never appears on the list page afterward" as if that were a silent-persistence-failure defect. It's technically true and practically meaningless: nothing about this site was ever supposed to add the tag to a list. This is a fourth generalization gap to set alongside Sauce Demo's three (§9) — not a crash this time, but a misleadingly-confident false positive, because the CRUD smoke flow's whole shape assumes a WidgetWorks-style "create it, see it in a list" pattern that doesn't exist on every site. Every other CRUD step (`update`, `delete`, `read-beyond-page-1`) correctly recognized it had nothing to work with and reported `skipped` with a reason, rather than fabricating a finding — only the `create` step's fallback path produced a false claim.

### Why this one matters differently than Sauce Demo

Sauce Demo (§9) mattered because it proved the tool's *engineering* generalizes — three real gaps, found and fixed, on a site that shares almost nothing with WidgetWorks except "it's a web app." This run matters for a different reason: it's the first time a finding was pushed all the way to a confirmed root cause using the target's own source code as a sanity check, and it's the first time the tool was handed inputs (checklist/charter/app-description) it had no way of knowing were wrong for the target — and it noticed anyway. It also surfaced the first false positive traceable to a specific, nameable design assumption (the CRUD flow's list-shaped mental model) rather than to noise or LLM variance. Two independent sites now, with two different kinds of evidence for the same underlying claim: not just "the tool finds real bugs it wasn't told about," but "the tool's own uncertainty signals are trustworthy enough to tell you when something doesn't fit," on two apps built by two different unrelated teams for two different purposes.

## 11. Defect patterns: what each method catches, what neither does

Three methods have now been scored against the full 41-fault WidgetWorks answer key: deterministic scanning and static AI review (together, the default pipeline — `measured-run-4`, §6), and live agentic browsing (`agentic-run-1`, §8). Cross-referencing which faults each one caught and missed, fault by fault rather than just at the aggregate-recall level, surfaces sharper patterns than either scorecard alone — and gives an evidence-backed answer to whether anything here needs a human. (The two external-validation sites, §9–§10, have no answer key and so can only corroborate qualitatively — this section is WidgetWorks-only, where ground truth exists.)

### Pattern 1: deterministic and AI review split cleanly along "mechanism" vs "meaning"

Of the 30 faults the default pipeline credited (found or partial), the per-finding source tags show three clean buckets, and each one has a distinct, nameable shape — not just noise:

- **Deterministic scan alone (4 faults: `CRUD-02`, `CRUD-04`, `CRUD-05`, `CRUD-07`).** Every one of these is a scripted before/after mutation-outcome check: does a create actually persist, does an update hit the right record, does a rapid double-submit race, does a delete actually invalidate a stale cache. No judgement is involved — a script that performs the action and diffs the result catches all four with zero LLM cost. The AI review never independently surfaced any of these on its own.
- **AI review alone (12 faults: `F-02`, `E-02`, `W-01`, `W-03`, `H-01`, `H-02`, `C-03`, `S-01`, `S-03`, `CL-02`, plus the `W-02`/`CL-03` partials).** Every one of these requires understanding *meaning*, not just checking a rule: an arithmetic contradiction (`H-02`, "founded 2018... 15 years"), a cross-field semantic mismatch (`W-03`, kg vs. lbs), a professional-judgement call about styling convention (`F-02`, a primary action styled as secondary), an unsubstantiated marketing claim (`CL-02`), or an accessibility violation axe-core's rule engine structurally cannot flag because it's contextual rather than syntactic (`S-01`'s placeholder-as-label passes automated a11y rules; `S-03`'s empty `alt` is technically valid on decorative images but wrong on informative product photos). No deterministic rule generalizes to any of these without effectively re-deriving human judgement in code.
- **Both, independently (14 faults).** These are faults with an unambiguous technical signature that also happens to be visually or contextually obvious — a real 404 image, a missing favicon, an inverted checkbox round-trip, contrast math. Both layers converging independently here isn't redundancy; it's the strongest-confidence category in the whole report, and it's also where false positives were lowest.

The practical implication: the two layers aren't interchangeable, and neither is a superset of the other. A pipeline that dropped deterministic scanning would lose the 4 mutation-integrity bugs entirely (AI review, working only from a static evidence bundle, has no mechanism to notice a silent non-persist). A pipeline that dropped AI review would lose the 12 meaning-dependent bugs entirely (no scripted rule was ever going to notice that "15 years" doesn't follow from "founded in 2018").

### Pattern 2: live, adaptive interaction resolves most of the static pipeline's misses — these are method gaps, not true blind spots

The static pipeline missed 11 faults (§6). Checking the same 11 against the agentic run's independent verdicts: **6 were fully caught by live browsing** (`E-03`, `H-03`, `P-03`, `S-04`, `CRUD-01`, `CL-01`), **1 improved from a full miss to a partial catch** (`H-04` — the agent found the color-mismatch symptom, though it still got the direction backwards, consistent with §9/§10's finding that neither pipeline has version-history awareness), and only **4 remained missed by both** (next section). That's 7 of 11 static misses resolved, at least partially, just by giving the AI a live browser instead of a fixed evidence bundle.

The reason each of these flipped is specific and instructive, not a generic "AI is smarter live" story:

- `CRUD-01` (negative price accepted) needed someone to actually *type a negative number in and submit it*. The static pipeline's form-validation probe (§Recommendation 3) only runs two fixed scenarios — empty, and non-numeric-text-in-a-numeric-field — neither of which happens to be "a syntactically valid but semantically nonsensical number." The agent, told to explore create-widget edge cases, tried it as a matter of course.
- `H-03` and `E-03` both needed a save to be performed and then a *specific follow-up property* (a timestamp, a success banner) checked — not just whether the record's own field values round-tripped correctly, which is what the static CRUD smoke flow's diffing actually checks. Same underlying mechanism (perform an action, inspect the result) but the static probe's diff doesn't look at that particular property.
- `CL-01` (contradictory customer counts) needed cross-referencing two specific numbers across two specific pages out of everything visible. The static pipeline's single cross-page synthesis call has to find this among every other cross-page thread in one pass; the agentic run, with a dedicated task and a narrower context per call, apparently had an easier time landing on it. (This is consistent with the general single-LLM-call variance caveat below — not evidence live browsing is structurally better at synthesis, just that it happened to work this time.)
- `S-04` (keyboard-inoperable sort control) is caught **by DOM-structure inference** ("built entirely from unsemantic div elements with no ARIA... cannot be operated by keyboard alone") — not by literally pressing Tab and Enter and observing what happens. Worth flagging precisely because it matters for the next section: this is a proxy judgement, not a real keyboard-driven test.
- `P-03` (dead PDF download link) simply wasn't in any of the static pipeline's four fixed interaction-probe categories (dropdowns, search, pagination, checkboxes) — a plain link/button that doesn't fit those patterns is invisible to the probe regardless of how obviously broken it is. General, unscripted exploration naturally covers ground a fixed probe list doesn't anticipate.

The common thread: the static pipeline's interaction probes are *precise but narrow* — a fixed, enumerated set of scripted checks. Live browsing is *broad but unscripted* — it goes wherever the model's own judgement about what's worth trying takes it. Six of eleven "misses" turned out to be a narrow-probe-coverage problem, not a fundamental limit of automation.

### Pattern 3: the static pipeline also catches things live browsing doesn't — this cuts both ways

The reverse cross-check matters equally: **12 faults the static pipeline caught were missed entirely by the agentic run** (`F-02`, `E-01`, `I-04`, `C-01`, `C-02`, `C-03`, `U-01`, `U-02`, `S-01`, `S-02`, `CRUD-05`, `CL-02`). The pattern here is just as specific: `C-01`/`C-02`/`C-03`/`S-02` are all **golden-reference visual/computed-style diffs** — and the agentic pipeline has no golden-reference comparison mechanism at all (§8's design deliberately gave it 6 bounded task prompts, not a scan-every-page-against-a-reference step). No amount of live interaction substitutes for a systematic diff the pipeline was never built to run. `CRUD-05` (double-submit race) and `U-01` (Cancel actually saves) needed a *specific* scripted action (rapid double-click; click Cancel and watch the network tab) that none of the 6 fixed agentic tasks happened to include — the mirror image of Pattern 2's `P-03` finding: fixed tasks miss what they don't anticipate, in both directions. And the static pipeline's exhaustive page-by-page sweep (every page, every time) simply covers more ground than 6 bounded tasks reliably will (`F-02`, `S-01` — pages the agentic tasks touched only in passing).

Breadth-with-precision (static) and adaptivity-with-blind-spots (agentic) are complementary failure modes, not one subsuming the other — reinforcing §8's original conclusion that agentic browsing is "a valuable supplementary signal, not a good default," now with the specific mechanism for *why* it's supplementary rather than superior.

### What neither automated method caught — 4 faults, and what each one actually needs

- **`F-03` — product cards have no hover feedback.** Neither pipeline ever captures or diffs a `:hover`/`:focus` pseudo-state. A human scanning the page naturally moves a mouse over things; nothing here does that on purpose. This is automatable (script a hover, screenshot, diff against the golden page's hover state) — it just isn't built.
- **`I-01` / `I-02` — logo and thumbnail images rendered at distorted aspect ratios.** Genuinely the most surprising pair in this whole dataset: the screenshot evidence was available to the AI review in both cases (twice — static and agentic both had a full-page screenshot of the offending element), and a human eye catches a squashed logo instantly, yet neither run's AI ever flagged it. This looks like a real LLM-vision limitation for this specific defect *shape* (subtle proportion distortion) rather than a missing scanner — and it's also trivially fixable deterministically: compute each `<img>`'s natural vs. rendered aspect ratio and flag a mismatch past a small tolerance, exactly the way `visualConsistency.js` already does for button radius and spacing. No AI judgement required; it just isn't one of the facts currently extracted.
- **`CRUD-03` — one specific item's detail page always 500s.** Both pipelines sampled a small number of catalog items (3 for the static CRUD smoke flow; whichever the agent happened to click) and neither one's sample happened to include the specific broken item (`w-005`). This is a coverage/sampling-budget limit, not a detection-capability limit — and it's the one item on this list that a time-boxed **human** exploratory session would be just as likely to miss, for the identical reason: nobody, human or automated, exhaustively clicks every item in a 24+ item catalog in one session.

Three of these four have a concrete, nameable automated fix (hover-state diffing, image aspect-ratio computation, broader item sampling) rather than requiring human judgement per se — the honest conclusion is that this dataset does *not* show a category of defect only a human could ever find. What it does show, credibly, is two narrower and more specific gaps:

- **Version-history awareness (`H-04`, §7/§9/§10) is the one fault that needs an entirely different oracle, not just a better probe or more sampling.** Every other miss in this document is fixable by extracting one more fact from the *current* page. `H-04` requires knowing what the page looked like *before* — version control, a changelog, a prior snapshot — a data source no method here has access to at all. A human tester with institutional memory of "wait, didn't this used to be a different blue?" would catch this trivially; none of these three methods can, structurally, until something adds a git-diff-aware scanner.
- **No method in this project ever literally drives a keyboard.** `S-04`'s catch was DOM-structure inference ("no ARIA, built from divs, therefore probably not keyboard-operable"), not an actual `Tab`/`Enter`/arrow-key walk through the page checking real focus order and activation. That inference happened to be right because the seeded bug was structurally obvious (a fully unsemantic custom widget). A subtler keyboard bug — a focus trap in a modal, a custom control that responds to click but not `Enter`/`Space`, a tab order that skips a field — would very plausibly *not* be visible from DOM structure or a screenshot alone, and nothing in this project's three methods (axe-core included — automated accessibility scanners are well known industry-wide to only reliably catch a minority of WCAG issues, and keyboard operability of custom widgets is specifically one of the categories they miss) actually exercises a keyboard to check. This is the clearest concrete "add real keyboard-driven interaction testing, or get a human/assistive-tech tester to do a keyboard-only pass" recommendation this dataset supports.

## 12. What's still unresolved / open questions

- **Single-LLM-call variance is real and only partially mitigated.** Both the per-page AI review and the adjudication pass are individual LLM calls. A multi-run majority-vote aggregator (`comparison/src/compare.js --runs N`) was added for adjudication specifically, but the AI *review* phase itself (the thing that produces findings in the first place, not just scores them) is still a single pass per page — a different run of the same tool against the same unchanged app could plausibly find a somewhat different subset of judgement-based issues.
- **Resolved: "everything validated against one synthetic app" (§9 and §10 address this directly).** WidgetWorks was designed by the same process that built the tool, an obvious risk of unconscious overfitting. Pointing the unmodified tool at Sauce Demo (independently built, structurally different — SPA, login-gated) and then at Shady Meadows B&B (a different tech stack again — hybrid SSR/CSR, no login gate, seven-microservice backend) — and having it find real, independently-verifiable defects on both, including one traced to a confirmed root cause in the second site's own source — is real evidence against that risk, from two unrelated codebases rather than one. Residual caveat: it's still only two external sites, both demo/training apps rather than production systems; a broader sweep across several independent, production-grade sites would be stronger evidence still.
- **The git-history gap (§7) is unimplemented, not just unmeasured.** Adding it is a materially different kind of scanner (diffing against a VCS, not just the live DOM) and wasn't attempted here. §11's fault-by-fault cross-check confirms this is the single defect in the whole answer key that no amount of better probing or more live interaction would fix — it needs a genuinely different oracle, not a better version of what's already here.
- **No method in this project ever literally drives a keyboard (§11).** `S-04` was caught via DOM-structure inference, not an actual `Tab`/`Enter`/arrow-key walk-through checking real focus order and activation — every automated a11y check here (axe-core and AI review alike) is a proxy for keyboard operability, not a direct test of it. A subtler keyboard-trap or broken-activation bug would plausibly slip past all three methods as currently built.
- **The regression-test-generation loop (Planner/Generator/Healer) couldn't be demonstrated live in this session** due to the nested-subagent limitation in §5.7 — the tests exist and correctly fail red against the still-buggy app, but they were authored directly rather than through the actual MCP-driven Generator tool-loop, and the Healer self-repair step wasn't executed at all (documented as a should-work-if-run-correctly scenario, not a verified one).
- **Cost and latency were not rigorously tracked for the static pipeline** (roughly $0.03–0.05 per `claude -p` call, Sonnet, per-page review; a full pass on the order of $0.50–1 and a few minutes wall-clock) — **but were tracked precisely for the agentic experiment** in §8 ($3.04 / 1402s across 6 tasks, logged per-task), which is itself worth noting: the more expensive, less-default approach got the more rigorous measurement simply because the experiment was designed around capturing that data from the start. Worth doing the same for the default pipeline before making any cost-at-scale claim in the post.
- **The agentic experiment (§8) is a single run, same variance caveat as everything else here.** One session, 6 tasks, one adjudication pass. The specific faults it happened to catch or miss could shift on a re-run the same way the static AI review's `CL-01`/`I-01`/`I-02` catches flickered between the two static-pipeline runs in §6's own results.
- **The Sauce Demo generalization fixes (§9) are themselves only tested against one SPA's specific conventions** (form login, `history.pushState` routing, `href="#"` + click handlers). A site using a fundamentally different pattern — OAuth redirect login, hash-based routing, a framework router with no discoverable click targets — would likely surface a fourth gap not yet found or fixed. Shady Meadows B&B (§10) didn't test these fixes at all — its routing is conventional enough that none of the three fallback paths ever activated — so it adds no new evidence either way on this specific point.
- **The CRUD smoke flow's list-shaped assumption (surfaced by §10) is a live false-positive risk, not just a theoretical one.** It correctly self-reports `skipped` with a reason when it can't find an update/delete/pagination target, but its `create` step instead falls back to filling *any* form it can find and treats "the tag doesn't show up on a list" as a finding — which is misleading on any site whose forms aren't all list-backed (contact forms, booking forms, search forms). Worth hardening before trusting a `create`-step finding against a new site without a human sanity-check first.

## 13. Threads for a feasibility verdict (interpretation, for the post to take a position on)

- The evidence here supports "meaningfully automatable, not fully automatable" rather than either extreme. A hybrid deterministic+AI tool independently found the majority of a diverse, deliberately-varied set of seeded defects (spanning accessibility, branding, functional correctness, data integrity, and cross-page claims) with zero access to the answer key — that's a real result, not a toy one. Corroborated, not just claimed: the same tool, unmodified in its detection logic, found real, independently-verifiable bugs on two real external sites it had never seen, built by two unrelated teams (§9, §10) — including, on the second, a finding pushed all the way to a confirmed root cause in the target's own source code, not just a plausible-sounding guess.
- The most transferable lesson is probably **not** "AI can do exploratory testing" — it's that **a large fraction of what looks like it needs human/AI judgement actually just needs someone (or something) to click the thing and check what happened.** The deterministic-layer expansion in §6 did more for recall, at a fraction of the cost, than anything about the AI layer's prompt or model choice — and on Sauce Demo, the single deterministic catch (the broken sort control) cost nothing beyond the scan itself, no LLM call required.
- The AI layer's comparative advantage, based on what it *did* catch that deterministic scanning structurally cannot — is judgement about intent and expectation: whether copy oversells a feature, whether a claim on one page contradicts another, whether a UX pattern violates a convention a user would reasonably expect, or — as on Sauce Demo — whether six product photos that are technically all "valid images that loaded successfully" are nevertheless all identical and therefore useless, or — as on Shady Meadows — whether two legal pages quietly name two different wrong companies as responsible for user data. That's a genuinely different capability from "did the DOM change after I clicked this," and the PoC's clearest evidence for AI's distinct value is concentrated there.
- **"Automate exploratory testing" turns out to be at least three different questions with three different answers**, and the post should probably say so explicitly rather than picking one: (1) can scripted, deterministic checks replace a lot of manual clicking? Yes, cheaply and reliably (§6), and it generalizes to sites with entirely different architectures once the crawler itself is taught the new architecture's conventions (§9, §10). (2) Can a static AI review add judgement-based value on top? Yes, but with real run-to-run variance (§12). (3) Should an AI agent drive the browser live like a human? Sometimes worth it for specific blind spots, but not as a cost-effective default (§8). Collapsing these into one "is AI exploratory testing feasible" verdict would flatten the most useful finding.
- The honest caveats (single-run variance in *every* mode tried, an unimplemented history-awareness gap, a nested-agent limitation that blocked a live regression demo, an oracle-trust bug that fooled both a script and an LLM the same way, three real generalization gaps found on Sauce Demo plus a fourth — a nameable false-positive pattern in the CRUD flow — found on Shady Meadows) are all worth keeping in the post rather than smoothing over — they're specific and falsifiable, which is more persuasive than a clean success story would be.
- **"Are there blind spots only manual testing could catch?" turns out to have a more precise answer than a flat yes or no (§11).** Of the 41 seeded faults, only 4 were missed by *both* the static deterministic+AI pipeline and live agentic browsing — and 3 of those 4 have a concrete, nameable automated fix (hover-state diffing, image aspect-ratio computation, broader item sampling), not a requirement for human judgement. Genuinely distinct from "needs a human" is "needs a different kind of automation than what's been built here" — most of this project's residual misses are the latter, not the former. The two real exceptions are narrower and more specific than "AI can't do exploratory testing": version-history awareness (needs an oracle — a VCS diff — no method here has access to at all, not just a better probe) and literal keyboard-driven interaction testing (nothing in this project, including axe-core, actually presses a key and checks what happens; the one keyboard-related catch was a DOM-structure inference that happened to be right, not a real test). If the post makes a "hire a human for X" recommendation, these two are the evidence-backed candidates — not a vague appeal to human intuition.

## 14. A third external target, with ground truth restored: BrightBasket

§9 and §10 deliberately validated against sites with no answer key — real evidence the tool finds genuine bugs, but only qualitative. A third target closes that gap while still being a genuinely independent codebase: **BrightBasket**, a sibling proof-of-concept (`ExploratoryTestApp`, a separate repo/directory next to this one) built to the same shape as WidgetWorks — its own checklist/charter/app-spec/test-app plus a hidden 48-fault answer key — but a materially different app: a small e-commerce storefront (browse → basket → two-step checkout → confirmation → order history) rather than WidgetWorks' flat inventory-CRUD shape. That difference is what makes this section worth writing: the checkout wizard exposed a real, previously-unseen class of generalization gap, and fixing it produced the clearest before/after data point in this whole project.

### The gap: pages that only exist after a valid multi-step form submission

Pointing the unmodified static pipeline at BrightBasket for the first time produced a recall of just **25%** (`brightbasket-static-1`, 3-run majority vote, range 24–25%) — barely above the very first WidgetWorks baseline (§3's 59%) and well below every prior external-validation result. The adjudicator's own per-fault reasoning made the cause obvious rather than mysterious: over and over, `"Checkout-payment page was explicitly not reviewed in this session"`, `"Confirmation page not reviewed"`, `"Basket was captured empty"`. Three whole page templates — `checkout-payment.html`, `confirmation.html`, and (transitively) `order-detail.html` — were **never visited at all**, and `basket.html` was only ever captured in its empty state.

The root cause, once traced through the app's own JS: `crawler.js` discovers pages exclusively via real `<a href>` elements (plus a click-test fallback for `href="#"`/`onClick`-only SPA navigation, added for Sauce Demo in §9). BrightBasket's checkout wizard advances via a plain `window.location.href = '/checkout-payment.html'` redirect *inside a form's `submit` handler*, after a successful `POST` — not a link, not an `onClick`-driven anchor, not any DOM element the crawler's click-candidate selector (`a[href="#"], a:not([href]), [data-test*="link"]`) would ever try. This is a **different kind of invisibility** than anything the tool had hit before: Sauce Demo's gap (§9) was about *how* a real destination gets reached (click vs. href); this one is about a destination that structurally doesn't exist to be reached at all until a valid, multi-field form has actually been submitted. No amount of smarter click-discovery fixes it — the crawler would have to submit forms with plausible data to find out what's behind them, which is a fundamentally different, riskier kind of "discovery." And `basket.html`'s empty-state markup in this app renders a *materially smaller DOM* than its populated state (no discount form, no per-line quantity input, no shipping-note text at all) — an empty capture doesn't just miss basket-specific bugs, it hides the majority of that page's surface from any reviewer, human or AI, looking only at the frozen snapshot.

### The fix: a checkout-walkthrough scanner, run before the crawl

Rather than teach the general-purpose crawler to guess at form submissions (unsafe to generalize — arbitrary forms have side effects), a new scanner (`exploratory-tester/src/scanners/checkoutWalkthrough.js`) drives the real conversion flow end to end — add to basket, reach basket, proceed to checkout, fill delivery details, fill payment details, place the order — using the same generic role/label/placeholder-heuristic discipline `crudSmoke.js` already established (accessible-name regex matching, not hardcoded selectors), so it activates the same way on any similarly-shaped app rather than being BrightBasket-specific. Two design points made it actually work end to end:

- **It runs *before* the crawl, not just before evidence capture.** `orders.html` only ever renders a real `<a href="/order-detail.html?id=...">` once at least one order exists — a fresh install has nothing there to discover. Placing a real order first means the *existing, unmodified* crawler picks up `order-detail.html` entirely on its own once it runs; no special-casing needed for that page at all. `checkout-payment.html` and `confirmation.html` are captured directly by the walkthrough itself (reusing the exact same evidence-capture routine — screenshot, DOM, a11y, console/network, form-validation probe, interaction probe — refactored out of the main per-page loop into a shared `capturePageEvidence()` so a page reached this way is first-class, not a special case with thinner evidence).
- **It tries the charter's own suggested edge-case values first, and falls back if they get rejected.** The charter explicitly calls for "deliberately awkward but valid" input (an apostrophe/hyphen name, a UK mobile with a leading zero, a single-digit house number) as part of a full timeboxed pass — so the walkthrough tries `"Siobhan O'Brien-Clarke"` first. On BrightBasket this **immediately reproduced a real seeded fault** (`U-04` — the name field wrongly rejects apostrophes/hyphens): the delivery form came back with `"Please check your details and try again."` and never advanced. Rather than let that dead-end the whole walkthrough (defeating the actual goal — reaching the pages behind it), it retries once with a conservative plain-text name and proceeds. A nice, unplanned side effect: the walkthrough's own retry-diagnostic log (`checkout-walkthrough.json`) is itself a clean, reproducible repro trace for `U-04`, captured as a byproduct of pursuing a completely different goal.

**A real bug found and fixed while building this, worth naming precisely because it's a generalizable lesson, not a BrightBasket quirk:** the first attempt used `page.getByRole("link", { name: /basket|cart|bag/i })` to find the "Basket" nav link. It matched the *header logo* instead and landed on the home page — because the logo's accessible name comes from its `<img alt="BrightBasket">`, and `"BrightBasket"` contains the substring `"basket"`. **Any accessible-name substring match is at risk of colliding with the product's own brand name**, and a brand name is exactly the kind of text that shows up disproportionately often near the top of the DOM (logos, headers), which is exactly where `.first()` picks it up. Fixed by anchoring the pattern to the *start* of the name (`/^\s*(basket|cart|bag)\b/i`) rather than a bare substring test — a fix worth applying to any future generic-selector heuristic in this codebase, not just this one call site.

### Results: recall nearly doubled, and the shape of the improvement is the interesting part

| Metric | `brightbasket-static-1` (pre-fix) | `brightbasket-static-4` (post-fix) | `brightbasket-agentic-2` |
|---|---|---|---|
| Recall (found + 0.5×partial) | **25%** (range 24–25%, 3-run) | **~45%** (range 43–46%, 3 independent single runs — see caveat below) | **52%** (range 51–54%, 3-run) |
| Found outright | 11/48 | 20/48 (stable across all 3 adjudication runs) | 24/48 |
| False positives | 24 | 2–8 (varied by run; roughly a third of the pre-fix count) | 7 |
| Bonus findings | 36 | 10–13 | 23 |
| Pages evidenced for AI review | 9 templates | 12 templates (+checkout-payment, +confirmation, +order-detail) | n/a (live browsing, no fixed page set) |

Category-level, the improvement concentrates exactly where the fix targeted it: **World 0/8 → 3–4/8** (the confirmation page alone carries 5 of World's 8 faults — house-number zero-padding, dropped phone leading-zero, reversed address order, the "working days" claim — all invisible until `confirmation.html` was evidenced at all), **Claims 2/5 → 4/5** (`CL-03`'s wrong Amex-digit hint and `CL-04`'s missing address-line-2 both live only on `checkout-payment.html`/`confirmation.html`), **Familiarity 0/3 → 2/3** (`F-01` and `F-02` — the missing logo link and the wrongly-secondary "Place order" button — are *both* checkout-payment.html-only defects), and **Explainability 1/4 → 2/4** (`E-02`, the raw JS error on payment failure, caught by *both* the deterministic form-validation probe and the AI review the moment that page was captured at all — zero incremental engineering beyond making the page visible).

**One real, honest regression, and it's instructive rather than embarrassing.** `U-01` ("basket can be empty and checkout still goes through") was **FOUND in the pre-fix run and MISSED in every post-fix run.** The reason is exactly the flip side of the fix's own benefit: `basket.html` is now *never* captured empty, because the walkthrough deliberately leaves one item in the basket afterward (see below) specifically so the *rest* of that page's surface — the discount form, the shipping-note text, the per-line quantity input — stops being invisible. But `U-01` is a bug that only manifests *in the empty state specifically* (checkout proceeds even with nothing in the basket), so making the basket reliably non-empty for evidence purposes trades away visibility into that one fault to gain visibility into several others. This is the same "narrow probes miss what they don't anticipate, in both directions" pattern already named in §11's Pattern 3 — the fix's own probe now has a shape, and that shape has an edge.

**A genuine false-positive introduced by the fix's own scaffolding, worth naming precisely.** Multiple adjudication runs credited a "bonus finding" along the lines of *"the basket badge still reads 1 on Order History/Order Detail after a completed order — the basket isn't cleared on checkout."* That's not a real observed defect — it's an artifact of the walkthrough's own last step, which deliberately adds a *second, unrelated* item to the basket immediately after placing the order (so `basket.html` isn't captured empty by the main crawl pass that runs afterward). The AI review, with no way to distinguish "this item survived checkout" from "this item was added moments later by the test harness itself," reasonably concluded the former. This sits in the same family as the Shady Meadows CRUD-create false positive (§10): a scanner's own scaffolding action, observed later without the scaffolding's own context, reads as if it were organic application behavior. Worth flagging in any future write-up of this fix rather than quietly absorbing it as a bonus finding.

### A second, unrelated engineering pitfall found while re-scoring this: concurrent `claude -p` spawns are unreliable on this machine, sequential ones are not

Running `comparison/compare.js --runs 3` (which fires 3 adjudication calls via `Promise.all`) against BrightBasket runs failed outright multiple times with a bare `claude -p exited 1` and **empty stderr** — no parseable reason, just a fast non-zero exit. The same pattern hit the agentic pipeline's later tasks on a first attempt (see below) and one static run's later per-page AI-review calls. Manually re-running the exact same call *sequentially, alone* succeeded every time on the first or second try. This reproduces cleanly enough to treat as a real, environment-specific characteristic rather than a one-off flake: **on this Windows/Git-Bash setup, spawning several `claude` CLI child processes at once (via `cross-spawn`) is measurably less reliable than spawning them one after another**, even though nothing about the individual calls changed. Practical consequence for this run: `--runs 3` had to be worked around by invoking `--runs 1` three separate *sequential* times and combining the results by hand (documented in the table above as "3 independent single runs") rather than trusting the built-in parallel majority-vote path for this target. This is a new item for a future "Engineering pitfalls" pass (alongside §5's list) — not yet root-caused (could be a Windows process-handle/pipe-buffer limit, could be a client-side rate limit that's stricter for burst-concurrent requests than sustained sequential ones), but reproducible enough to plan around: prefer sequential adjudication runs over parallel ones on this platform until the actual cause is found.

### A third, separate pitfall: the agentic mode's hardcoded task list, and its hardcoded per-task budget

Two more real gaps surfaced running the *agentic* (live MCP-browsing) pipeline against this new target, both fixed generally rather than patched around:

1. **The 6 built-in agentic tasks (`runAgenticSession.js`) are WidgetWorks-shaped by name** ("Go to the 'Add widget' form...") — pointing agentic mode at BrightBasket unmodified would have run those exact prompts against a site with no widgets at all. Fixed by adding an optional `--tasks-file <path.json>` flag (`config.js`) that loads a `{id, description}[]` array, falling back to the original list (renamed `DEFAULT_TASKS`) when omitted — every prior agentic result stays reproducible with zero flag changes. `external-validation/brightbasket/agentic-tasks.json` holds BrightBasket's 7-task set, written from the charter's own Target Areas table alone, before the answer key was read for scoring.
2. **The default `--max-budget-usd 0.50` per task, inherited unchanged from WidgetWorks, was too tight for these broader tasks.** A first full run (`brightbasket-agentic-1`) succeeded on task 1 ($0.33) then failed the remaining 6 with the exact same bare "exited 1, empty stderr" signature as above — but with the *full* task wall-clock time elapsed first (200–250s each), which is what pointed at a budget cap rather than a crash: the model did real work, then got cut off at the end rather than failing fast. WidgetWorks' 6 tasks were deliberately narrow ("select each sort option," "click delete"); several of this run's 7 tasks are intentionally broader composites (e.g. "apply all four discount codes, checking totals after each") that need proportionally more turns. Raised to `--max-budget-usd 1.50` and reset the app's data, and all 7 tasks (`brightbasket-agentic-2`) completed cleanly — $5.28 total, ~41 minutes, none hitting the new cap by more than half.

### Why this result matters more than the recall percentage alone

Every number above is good corroborating evidence, but the actual headline is structural: **a whole category of generalization gap — pages that exist only behind a valid multi-step form submission, not any kind of link or click-handler — was invisible to this architecture until a target with that specific shape (a checkout wizard) was actually tried.** Sauce Demo (§9) taught the tool about SPA click-routing; Shady Meadows (§10) taught it that a CRUD-shaped smoke-test assumption doesn't hold on every site; BrightBasket teaches it that "crawl every reachable page" is a *narrower* definition of "reachable" than it sounds, and that closing that gap needs a dedicated, purpose-built scanner (drive the flow, don't just discover pages) rather than a smarter crawler. Recall nearly doubling (25%→~45%) on the exact same unmodified checklist/charter/app-description, purely from making three more page templates visible to the AI review that was already there, is the sharpest illustration in this whole project of §13's core thesis: a large fraction of what looks like a detection-capability gap is actually a coverage gap.
